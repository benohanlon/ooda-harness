# Private harness home template

Adapt this small map in your chosen private home. Reuse existing files and record owners; the headings below are prompts, not a required directory tree. The [Sovereign Profile template](sovereign-profile-template.md) supplies the personal portrait. The [role template](../roles/ROLE-TEMPLATE.md#assemble-this-role) supplies role assembly and its individual contract. Copy the [sovereign role sleeve](../roles/ROLE-TEMPLATE.md#sovereign-role-sleeve) for a chosen role. When you commission an eval group, copy the [group template](eval-group-template.md) and link the completed Markdown from that role's sleeve.

## Private README: start here

Explain whom this home serves, the work it supports and where to begin. Keep one canonical personal profile, retrieving relevant detail rather than loading every file.

Name the shared harness `ooda-harness` and the private application `sovereign-<individual>-harness`. The generic example is `sovereign-individual-harness`; replace `individual` with the person's chosen identifier, for example `sovereign-alex-harness`. Its display name can be **Sovereign Alex Harness**. These identify the harnesses without requiring GitHub storage, a new repository or a separate directory per role. Keep `sovereign.md` as the personal portrait when that convention is used. For an existing home, record its actual address separately from a proposed name and use the [update path](getting-started.md#update-an-existing-installation) before changing active bindings.

| Need | Record the maintained route and status |
| --- | --- |
| Personal context | Profile entrypoint, relevant answers and communication preferences, or the resolved choice to proceed without one. |
| Shared basis | Source location and full accepted revision. Distinguish a proposed update from the revision currently accepted and installed. |
| Configuration and recovery | Existing installation record and private binding owner: managed adaptations, startup routes, previous working revision and refresh procedure. Keep credentials outside tracked content. |
| Chosen roles | Role directory or existing map: each role's selected shared definition/revision, private application, relevant system-wide units of account and status. Use the shared template and common contract where no reference role exists. Connect relevant relationships, memory and experience through their owners. A catalogue role or assembly ticket does not appoint participants. |
| Current work | Current assignment and authoritative project/case records, with the permitted source access needed for that work. |
| Reusable experience | Selected case routes, including later corrections, observed results or limits, permission and a cue for when to retrieve them. Keep originals with their maintained owners. |

Mark an unresolved route **pending**, name what must be recovered and give the next action. Do not substitute a guessed link. Ordinary personal context should be usable without the template author's private services; a particular live assignment may still need its own authorised source connection.

These entries connect [shared machinery and sovereign sleeves](../README.md#shared-and-private-harnesses). Separate files or sleeves only where purpose, stewardship, access or lifecycle warrants it. Projects can remain independent. Private experience does not become a shared contribution automatically: select permitted material, remove private dependencies, review the proposed improvement, then adopt an accepted shared update deliberately.

## Private AGENTS: orient an arriving agent

Keep a short private `AGENTS.md` alongside the human-readable README. Route the agent to the selected accepted shared basis through the configuration owner, the sovereign profile, chosen-role directory and relevant role contracts. Reuse maintained guidance rather than copying shared repository contribution rules or whole policies. The role directory can remain `roles/README.md`; its filename need not match shared `ROLES.md`.

The setup owner configures and verifies how the selected runtime receives this guidance through [instruction loading](getting-started.md#configure-instruction-and-skill-loading). Matching filenames do not establish automatic loading or inheritance. Preserve existing project instructions and the private-profile connection.

## Optional unfinished-work stub

Use this where an agreed next piece needs a durable home before it is built. Use or update an existing ticket or task record rather than creating a second queue.

| Field | Supply |
| --- | --- |
| Status and purpose | Clearly unfinished; what useful outcome this work should produce. |
| Maintenance owner | The person or existing workstream maintaining this stub; distinguish that from a future role appointment. |
| Basis and routes | Accepted decisions, relevant shared method/template, authorised private inputs and current project owner. |
| Missing work | Exact decisions, inputs or implementation still needed, including unavailable routes. |
| Next action | The smallest authorised move and any material dependency. |
| Completion evidence | What must be saved and checked before this stub can be replaced or closed. |

A role assembly ticket should connect the selected shared basis and private application into [one governing nucleus](ecology-of-mind.md#combined-role-basis) with its purpose, accountability and relevant system-wide units of account. Select [direct or paired work](operating-contract.md#choose-the-working-arrangement) for the current bounded assignment and supply each commissioned participant with that whole relevant basis, private relationship and experience. Use the existing assembly path for actual contexts, capabilities, records and recovery; reciprocal paired work requires two supplied contexts. Preparing a contract is distinct from commissioning participants or demonstrating useful operation. Installation can finish while that role work remains pending.
