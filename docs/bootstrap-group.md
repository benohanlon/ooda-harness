# Bootstrap a role group

**Procedure for a configured harness.** Initialise or resume one commissioned role in an existing group. This connects actual participants to the accepted role basis and first useful work; it does not install Hermes, create profiles or prove continuing paired operation. Use [package bootstrap](bootstrap.md) only if an installation is missing or needs an authorised update.

## Short entry instruction

Supply an accessible link to this file at the accepted full commit in the user's shared repository or fork. Use an existing authorised repository connection or matching verified snapshot; an anonymous private-file 404 alone does not establish that the file is absent. Report exact missing access without exposing credentials or changing permissions.

> Bootstrap this existing group as [role] following [accepted-revision link to docs/bootstrap-group.md]. Use our connected private role application and existing profile-function mapping; private role/continuation route: [known route, or resolve through the existing binding]. Recover any current assignment and continuation. First assignment: [outcome, scope, authority and effort/return condition], or report ready if no assignment is supplied.

Take source locations, identities and record owners from current steering and existing private bindings. Clarify only material unresolved inputs. The reusable procedure contains no user's private paths, account identifiers, measures or work history.

## 1. Recover the role and actual participants

Identify the sovereign served, commissioner, reporting recipient, existing group, actual participant contexts and profile functions. Inspect supported runtime identity and available capabilities rather than trusting titles. Reconcile supplied functions with the accepted private mapping; explicit current steering can deliberately change that mapping. Preserve existing histories, local adaptations and working installations.

Use the private role directory and contract to find the selected shared reference, its common rules, current brief, relevant private context and source owners. Preserve explicitly selected role foundations rather than adopting a newer branch head. Where no shared reference exists, the accepted [role template](../roles/ROLE-TEMPLATE.md#assemble-this-role) and [common contract](operating-contract.md) supply the shared structure. A file's presence does not appoint a role. The sovereign's explicit current appointment or assignment can supply that commission; proceed within its stated scope without requesting the same approval again. Resolve only material gaps in an undefined role before dependent work.

For the Hermes three-profile arrangement, follow [the runtime mapping](runtimes/hermes.md#interface-and-two-reusable-participants): interface plus two reusable participant profiles, with separate continuing role-room contexts. The interface carries intent, relevant context and steering, integrates the return and preserves material disagreement. It is a thinking partner and coordination function; the Twins remain the two role participants. Neither a third Twin nor automatic access to every profile conversation is implied.

## 2. Supply the whole basis and orient together

Each actual participant retrieves the selected SOUL, shared role definition/common rules, private application, current brief and relevant private/source routes. Supply both Twins the same relevant governing basis and starting specification required by their selected contract. Verify actual model/capability access against that requirement and record any deliberately authorised adaptation; do not change provider configuration merely to initialise a room. Distinguish configuration, guidance present at startup, references opened now and actual observations. Retrieve changed governing material explicitly where startup is stale; report the loading limit without rewriting native prompts or bypassing session ownership.

Use authorised maintained sources. Commissioning the role does not grant blanket permission to disclose private conversations into the room; respect the installed native room protocol and the sources' disclosure boundaries.

Understand three connected things:

- **Nucleus:** the combined shared/private governing basis, including the role contract, purpose, accountability and relevant axis.
- **Axis:** the relevant system-wide units of account selected through that basis. Retrieve definitions, acceptance status and current evidence from their existing owners. Preserve qualitative value alongside measures; do not invent targets, weights or a composite score.
- **Orientation:** a revisable working understanding of the sovereign's intention, self, peers, other actors and unfolding circumstances. The [operating model](../README.md#4-operating-model) and [ecology of mind](ecology-of-mind.md) explain the relationships.

Build enough mutual understanding for the assignment: whom the role serves and why; what each participant can access, has actually examined, currently interprets and owns; what the other participants need from it; and which assumptions or outside responses could change the next move. Retrieve relevant prior decisions and corrections. Distinguish the sovereign's stated intent from inferred preferences and each participant's provisional interpretation. Ask or test a consequential uncertainty rather than inventing a personality, motive or shared memory. Retain only decision-relevant understanding with the existing brief/checkpoint; no separate theory-of-mind store is required.

The contract does not contain the whole orientation. The sovereign's correction, a peer's discovery or an external result can change it. Both Twins observe, orient, decide and act. Their doer/giver and observer/active-receiver emphases are relational and reversible; neither a fixed division of OODA stages nor a permanent author/critic hierarchy. Boyd's OODA informs this method; two-agent polarity is the harness's design, not a prescription established by Boyd.

## 3. Connect work, exchange and continuation

Recover or initialise the current assignment using the [existing bounded-assignment fields](operating-contract.md#bounded-assignment). Reuse its record owner. Establish the outcome, current evidence, authority, effort, initial complementary positions, action owner for each shared effect, recipient and return condition. A polarity change does not transfer write or decision authority.

Verify a supported exchange route between the actual contexts. Use native room handoffs, not imagined internal conversations. Both can investigate, offer alternatives and reorient work while it can change; assess material contributions against sources and current steering. Agreement, dissent and a set number of turns are not the objective. Work need not wait for every bounded worker to return before a consequential finding changes the approach. Missing exchange means paired operation is pending or degraded, not that a fluent solo answer counts as the pair.

Keep the group-to-role/source/record route discoverable through the existing private assignment or deployment owner. Supply that route on first entry, a new thread or replacement when the native runtime does not inject it. A historic room message or profile-wide memory is not a verified room-level instruction loader. Verify actual working-directory/project context separately. Do not promise that an ordinary Master chat automatically dispatches to this room and receives its result.

Use the [checkpoint and restoration method](operating-contract.md#work-checkpoints-and-restoration): preserve material contributions and their dispositions, accepted steering, unresolved differences, completed/pending work, uncertain effects and the next owner/move. In read-only work, return the checkpoint in chat. Persist it only within the assignment's write authority. New threads and replacement contexts must recover the current basis and both perspectives before continuing dependent work. Saving a checkpoint does not schedule a wake or prove recovery.

If the latest checkpoint exists only in chat, supply that checkpoint or a verified native-history route on re-entry. An older private brief is not a substitute for the latest steering and result; report the exact missing continuation if it cannot be recovered.

## 4. Begin useful work and inspect the result

Give one brief readiness statement with the selected basis, actual participants and material gaps, then perform the authorised first assignment. Continue unaffected work when a source is unavailable; state reduced coverage. If no task was supplied, return ready with the exact next input needed rather than inventing work. For the first Chief of Staff application, use [Perception Check](../skills/perception-check/SKILL.md); another role uses its own appropriate task.

Use outside evidence and results to test expectations, not only internal agreement. Retain the decision or action advanced, unresolved uncertainty, feedback owner/return condition and the whole effort, including human reconstruction or chasing. OODA continues during work; the numbered setup sections are dependencies, not a four-stage reasoning pipeline.

Use [Evaluate a role group](evaluating-role-groups.md) to review the first result with the sovereign, retain consequential exchanges and develop a fair comparison. It applies the existing acceptance rules without making a benchmark programme a prerequisite for useful work.

The next follow-up should recover the same continuing contexts and latest checkpoint through the native mechanism. Observe loading, consequential reciprocal exchange, coherent return and continuation separately. Apply broader [runtime acceptance](operating-contract.md#runtime-acceptance) before claiming recovery, unattended persistence or comparative advantage. Initial useful work need not wait for a benchmark programme.

Re-running this entry resumes and reconciles; it does not duplicate contracts, participants or records. Shared source, private application, installed bindings and live task state retain their existing owners. Adoption or deployment of revised instructions remains deliberate.
