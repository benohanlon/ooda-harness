# Bootstrap OODA Harness

**Private alpha: agent-driven setup.** Give an existing assistant the short instruction below; the repository supplies the installation procedure. It needs repository access and permission to configure the selected destination. This does not install the assistant runtime itself or establish that a role pair is operational.

## Copy into chat

Replace the bracketed inputs. Use a full accepted commit SHA that contains this file so the instructions and installed package come from the same revision. Older releases without this entry point still use their own Getting started guide; do not mix a new bootstrap with an older pin silently.

> Bootstrap OODA Harness by reading https://github.com/benohanlon/ooda-harness/blob/[accepted-commit]/docs/bootstrap.md and following its installation procedure. Target: [this environment or a named profile/workspace]; function: [interface, participant-a, participant-b or general]. Use my existing private-harness connection, or resolve it through the guide.

If supplying a new private repository, add its location and accepted revision. Do not put credentials in the prompt. A private repository link is usable only after this assistant has authorised access. A fork can substitute its own repository and accepted revision.

The function is the target's place in the deployment, not an enduring operating role. `participant-a` and `participant-b` can wear different role hats. The agent verifies the actual runtime identity; a name or highlighted sidebar item is insufficient.

## Installation procedure for the receiving agent

1. **Resolve the destination and existing state.** Read the selected package's [README](../README.md), [SOUL](../SOUL.md) and [AGENTS](../AGENTS.md), retaining repository contribution rules at their project scope. Identify runtime/version, execution host, actual profile home or workspace, current installation record and private connection. Use supplied values and existing bindings; ask only for material unresolved inputs. A remote Desktop's local disk is not the remote backend's disk. Recover or record the supplied profile-function mapping with its existing private deployment owner. Scope this run to the named target; creating other profiles, groups or roles needs that scope in the assignment.

2. **Select first install, update or recovery.** Follow the corresponding path in [Getting started](getting-started.md). Compare existing managed files and later local corrections before writing. Back up affected configuration and guidance. Repeating a bootstrap at the same revisions should retain matching files and report unchanged configuration; it must not create another profile, reset memory or duplicate instructions.

3. **Obtain and verify the sources.** Fetch the accepted shared commit from its authorised GitHub origin, or reuse a verified matching snapshot. Confirm origin, exact commit and clean tracked source content; keep the complete package and its references together. Resolve and verify the separately selected private source through its existing connection. Check remote read access to both repositories when GitHub is their source. A successful fetch proves reading, not read-only permission: identify the credential used and inspect its granted permissions without exposing secrets or attempting a push. If that evidence is unavailable, report permission verification pending. Do not broaden access to complete a check or silently replace a pin with the latest branch head.

4. **Use the runtime's supported loading route.** Follow [Hermes](runtimes/hermes.md) or [Codex](runtimes/codex.md) setup notes. If no supported mapping exists for the target, retain the sources and report the missing adapter instead of inventing configuration. Supply the complete accepted source packages and selected skill folders with dependencies; configure startup guidance and retrieval routes. Preserve independent writable state, unrelated settings and source snapshots. Keep any profile-function adaptation outside the accepted shared source and record it. Complete package availability is different from preloading every skill, role and private record into every prompt.

5. **Finish the private connection and verify loading.** Perform [Finish installation: connect your private profile](getting-started.md#finish-installation-connect-your-private-profile), preserving a working connection or an explicit choice to continue without one. Read back managed files, required references and private entrypoints. Use a fresh or supported refreshed context to verify actual startup loading; an explicit file read alone proves access. Respect native session ownership and coordinate any refresh with the owner. A busy or refused session is not permission to launch another writer on its profile home.

6. **Return a usable receipt.** In the existing private installation record retain target/function, source origins and revisions, managed files, local adaptations, private loading route, access/permission evidence, rollback and exact remaining work. Keep credentials and native databases out of shared source. Give the user a short result distinguishing installed or unchanged configuration, verified loading, pending checks and the next action. Do not call the bootstrap complete while required configuration/loading checks remain unresolved. If installation alone was requested, leave role commissioning pending.

For the interface plus A/B arrangement, follow the [Hermes three-profile section](runtimes/hermes.md#interface-and-two-reusable-participants). Both participants receive the whole relevant shared/private basis. Profile function does not grant authority over other work or change the shared role's accountability.

## Runtime and packaging limits

This is a maintained procedure for an agent with the required tools, not an unattended installer or a claim of identical behaviour across models and hosts. Reproducibility starts with the same verified sources; runtime versions and local adaptations remain recorded deployment inputs. Permission prompts, unavailable private sources and unsupported runtime controls can require the user.

Prefer Hermes's native [profile distributions](https://hermes-agent.nousresearch.com/docs/user-guide/profile-distributions) over a custom installer when packaging is justified. This repository is not yet a tested distribution. The [inspected upstream installer](https://github.com/NousResearch/hermes-agent/blob/fcc26fbd9f1641755e49793d7ed608f3b7214c3d/hermes_cli/profile_distribution.py) refuses the built-in default profile, requires deliberate conversion of an existing non-distribution profile, and shallow-clones a Git source without selecting an exact ref. Verify installed support before prescribing commands. A verified local staging directory can supply a pinned payload, but the bootstrap must retain its Git provenance and controlled refresh. The adapter must declare owned files, preserve complete reference routes and local function adaptations, and still connect the private harness. Do not force-convert live profiles or treat `hermes profile install` against this raw repository as a working setup. No native package or installer script is introduced here.
