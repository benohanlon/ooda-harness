# Bootstrap OODA Harness

**Private alpha: agent-driven setup.** Give an existing assistant the short instruction below; the repository supplies the installation procedure. It needs repository access and permission to configure the selected destination. This does not install the assistant runtime itself or establish that a role pair is operational.

## Two parts, one personalised deployment

A full personalised bootstrap supplies both the shared OODA foundation and the sovereign individual's separately maintained private harness. The shared package provides the reusable structure; the private half supplies that user's personal context, selected sleeves, role applications and authorised source routes. Both parts must be connected and accessible in each target that uses them. One shared distribution is not the whole personalised harness.

The published bootstrap contains only this connection contract and generic placeholders. Never embed a user's private harness contents, account identifiers, runtime paths, transcripts or credentials in the shared repository, distribution, example prompt or public receipt. Do not assume the installer is the harness author or derive a private repository from their name. Resolve the user's existing private binding on the target, or ask for their own location and authorised access. Retrieve and retain private material only in that user's authorised private environment; keep the source mapping and deployment receipt private. A native shared-profile installer does not automatically fetch or merge a second private source.

The two halves need not occupy separate repositories. Inspect the existing private binding, its README/agent entrypoint and explicit source routes first. If a private checkout contains both a shared-package snapshot and the user's sleeves, reuse that arrangement and verify the selected shared basis separately. Otherwise use the connected private repository, folder or chosen store. Keep private content in a private destination, preserve uncommitted work, and do not search unrelated repositories or infer a private location from an account name. Ask for the location only when those routes leave it unresolved.

When the user supplies a fork, treat that fork and its accepted commit as the shared source; verify its origin and retain upstream separately as an optional update source. Do not hard-code the original author's account or adopt newer upstream content automatically. Check the destination's visibility: [public GitHub forks remain public](https://docs.github.com/en/pull-requests/reference/forks#visibility-of-forks), and private fork networks can share access/history. Keep personal sleeves in an appropriately private store; a public shared fork is not that store.

## Copy into chat

If the harness is already installed and the assignment is to initialise or resume a role group, use [Bootstrap a role group](bootstrap-group.md). Reuse its installations and selected role foundations; group commissioning does not require another package installation.

When the installed runtime can discover [Deploy Harness](../skills/deploy-harness/SKILL.md), a request such as “Check for accepted harness updates and apply them to these profiles” invokes this same procedure. The skill coordinates the shared package and the user's private source. It does not create a second installer or assume the creator's private harness.

Replace the bracketed inputs. Use a full accepted commit SHA that contains this file so the instructions and installed package come from the same revision. Older releases without this entry point still use their own Getting started guide; do not mix a new bootstrap with an older pin silently.

> Bootstrap OODA Harness using [accepted-revision link to docs/bootstrap.md in my shared repository or fork]. Target: [this environment or a named profile/workspace]; function: [interface, participant-a, participant-b or general]. Use my existing private-harness connection, or resolve it through the guide.

If supplying a new private repository, add its location and accepted revision. Do not put credentials in the prompt. A private repository link is usable only after this assistant has authorised access. A fork can substitute its own repository and accepted revision.

Optional application connections and two-way chat visibility follow [Connection assembly](connections.md). Configure only the commissioned destinations and permissions, retaining verification in the existing private deployment receipt. These connections are not silently installed by package bootstrap.

The function is the target's place in the deployment, not an enduring operating role. `participant-a` and `participant-b` can wear different role hats. The agent verifies the actual runtime identity; a name or highlighted sidebar item is insufficient.

## Check for updates or refresh

You can ask the assistant already using the harness:

> Check whether an OODA Harness update is available for this installation, including my private harness and existing role bindings. Report the installed and candidate revisions, material changes and held selections. Do not activate changes yet.

Or commission the update:

> Refresh this installation to the current accepted shared and private harness sources. Preserve my local changes and existing work. Reconcile the project and group bindings for its already commissioned roles, verify loading and report anything left held or pending.

Resolve sources through the existing binding and the user's acceptance policy. A newer branch head is an update candidate, not automatic adoption of upstream or an unaccepted proposal. Resolve each selected commit before writing and retain it for the whole run. "Check for updates" is read-only. "Refresh" or "pull and apply the harness" authorises the scoped update procedure, not a runtime upgrade, new roles or new connections. Ask only when the source acceptance or affected scope remains materially unresolved.

## Installation procedure for the receiving agent

1. **Resolve the destination and existing state.** Read the selected package's [README](../README.md), [SOUL](../SOUL.md) and [AGENTS](../AGENTS.md), retaining repository contribution rules at their project scope. Identify runtime/version, execution host, actual profile home or workspace, current installation record and private connection. Use supplied values and existing bindings; ask only for material unresolved inputs. A remote Desktop's local disk is not the remote backend's disk. Recover or record the supplied profile-function mapping with its existing private deployment owner. Scope this run to the named target; creating other profiles, groups or roles needs that scope in the assignment.

2. **Inspect and classify the installation.** Follow the first-install, update or recovery path in [Getting started](getting-started.md). Compare the recorded sources, managed files, local corrections, private connection and loading evidence before writing. With matching revisions, configuration and verified loading, retain the installation and report unchanged. With the same sources but stale loading or a missing managed route, perform only the justified refresh. With a newly accepted revision, stage and review the update while preserving local adaptations. With damaged or incompatible state, diagnose and use supported recovery; recommend redeployment only when a bounded repair is unsuitable. Redeployment does not authorise deletion, profile recreation or service interruption. Back up affected files and retain rollback before changes. A repeated run must not duplicate profiles/instructions, reset memory, or follow a moving branch head.

3. **Verify both sources and read-only access before activation.** Fetch the accepted shared commit from the selected repository/fork, or reuse a verified matching snapshot. Confirm origin, exact commit and clean tracked shared source content; keep the complete package and its references together. Resolve and verify the separately selected private source through its existing connection, preserving the private entrypoint, sleeves and uncommitted work. For this full GitHub bootstrap, read-only access to the repositories supplying both halves is a prerequisite on the actual execution host/profile. Identify the credential and authentication route used for each source, perform a read, and confirm its read-only grant from GitHub settings or permission metadata. A successful fetch, a promise not to push, or another machine's connection is not proof. Use explicit intended identities rather than falling back to a broader account credential. Co-located halves may share one verified origin/credential; record both logical source bindings without duplicating clones. Reuse recorded permission evidence only when its credential identity and repository scope match. Retain the inspection date and any explicit user acceptance of dated evidence; do not present it as a new settings check. Resolve contrary evidence or an unverified historical label before activation. If either read or its read-only grant cannot be verified, stop before activating or updating profile files and report that exact access blocker. Keep any source preparation, existing installation and private material intact. Do not expose secrets, attempt a push, broaden permissions or silently replace an accepted pin.

4. **Use the runtime's supported loading route.** Follow [Hermes](runtimes/hermes.md) or [Codex](runtimes/codex.md) setup notes. If no supported mapping exists for the target, retain the sources and report the missing adapter instead of inventing configuration. Supply the complete accepted source packages and selected skill folders with dependencies; configure startup guidance and retrieval routes. For existing commissioned roles in scope, follow [Check role bindings](getting-started.md#check-role-bindings) so project and group instructions select the intended shared definition, private sleeve and current brief. Preserve independent writable state, unrelated settings and source snapshots. Keep any profile-function adaptation outside the accepted shared source and record it. Complete package availability is different from preloading every skill, role and private record into every prompt.

5. **Finish the private connection and verify loading.** Perform [Finish installation: connect your private profile](getting-started.md#finish-installation-connect-your-private-profile), preserving a working connection. If the user explicitly chooses to continue without a private harness, record a shared-only installation with limited personal context; do not report the full personalised bootstrap complete. Read back managed files, required references and private entrypoints. Use a fresh or supported refreshed context to verify actual startup loading; an explicit file read alone proves access. Respect native session ownership and coordinate any refresh with the owner. A busy or refused session is not permission to launch another writer on its profile home.

6. **Return a usable receipt.** In the existing private installation record retain target/function, source origins and revisions, managed files, local adaptations, private loading route, read-only access evidence for both halves, rollback and exact remaining work. Distinguish package installation from each affected role binding and context refresh. Report the reason and next owner for a held selection or a role not yet commissioned. Keep credentials and native databases out of shared source. Give the user a short outcome: newly installed, unchanged, refreshed, updated, or repair/redeployment pending, supported by what actually happened. Confirm both halves, the read-only gate and required loading before calling a personalised bootstrap complete. If any part is missing, retain verified work and name the blocker/next action. If installation alone was requested, leave role commissioning pending.

For the interface plus A/B arrangement, follow the [Hermes three-profile section](runtimes/hermes.md#interface-and-two-reusable-participants). Both participants receive the whole relevant shared/private basis. Profile function does not grant authority over other work or change the shared role's accountability.

## Runtime and packaging limits

This is a maintained procedure for an agent with the required tools, not an unattended installer or a claim of identical behaviour across models and hosts. Reproducibility starts with the same verified sources; runtime versions and local adaptations remain recorded deployment inputs. Permission prompts, unavailable private sources and unsupported runtime controls can require the user.

The repository's `distribution.yaml` packages the shared foundation for Hermes's native installer. Follow [Hermes distribution setup](runtimes/hermes-distribution.md) for ownership, controlled source selection, installation and in-place updates. Native installation refuses the built-in default profile. Preserve existing non-distribution profiles through the established loading path until migration is commissioned. Do not force-convert live profiles. A verified local source supplies a deliberately pinned payload, while a Git-URL source follows its recorded default branch. Neither path connects the private half by itself. Updating Hermes software is separate from updating a distributed profile.
