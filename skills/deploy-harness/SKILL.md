# Deploy Harness

Head of Harness Engineering maintains this capability. Use the current commission to identify the runtime, target profiles or workspace, accepted sources and permitted changes. A profile is a runtime environment, not a role or user. A list of targets can grow beyond the initial interface and A/B arrangement.

## Choose the path

Read [Bootstrap](../../docs/bootstrap.md) for the shared/private connection contract, destination checks and first-install, update or recovery decision. It owns the procedure. Use [Hermes distribution setup](../../docs/runtimes/hermes-distribution.md) for native Hermes install/update mechanics or the [Codex runtime guide](../../docs/runtimes/codex.md) for Codex. Do not substitute Hermes profile commands for another runtime's loading mechanism.

Recover existing source bindings, local corrections and current work before changing anything. Resolve the user's own private harness through its existing entrypoint. Keep their contents, account routes and history out of the shared distribution. Verify the actual source access required by Bootstrap on the execution host. Do not infer access from this chat or another profile.

For a fresh recipient with no binding, resolve their private location and access through Getting started. Ask once when it is unknown and retain their choice privately. Help create a minimal private home when requested, adding sleeves for commissioned roles rather than duplicating them per profile. An explicit shared-only choice remains valid and must be reported as such.

## Carry out the commissioned change

Resolve the accepted revisions through [the recorded update policy](../../docs/bootstrap.md#choose-the-accepted-revisions). In Hermes, use native profile distributions for named profiles that support that path. Preserve an existing built-in `default` interface and non-distribution profiles through the established bootstrap path until a migration is explicitly commissioned. Never add `--force` to make a failed install succeed.

Keep [one private current receipt per target](../../docs/bootstrap.md#keep-one-current-receipt-per-target). Read it before changing the installation and update it with the active revisions and observed verification. Retain backups and prior results in the existing deployment history. A normal package update preserves personal state but can replace distribution-owned files. Check meaningful local edits before updating them. Do not silently repin a private role's selected shared reference.

Finish with the Bootstrap guide's [private-profile connection](../../docs/getting-started.md#finish-installation-connect-your-private-profile), reusing the working connection. Verify guidance loading and one useful commissioned action separately from file installation. Use fresh or supported refreshed contexts as the runtime requires. Do not infer success from files or greetings alone.

## Return a usable result

Report each target as unchanged, installed, updated, recovered or blocked, with the selected revision and material remainder. Distinguish private connection, loading, source access and useful execution. If a multi-profile change stops part-way, identify the exact mixed state and next owner. Do not claim an atomic fleet update.

When the next assignment is to set up a role group, hand over through [Bootstrap a role group](../../docs/bootstrap-group.md). Reuse installed profiles and sources. This skill does not appoint roles, create all available groups, connect every account or start schedules automatically.

## Package dependencies

This skill ships with the complete OODA foundation. Its linked Bootstrap, Getting started, runtime and group guides must be supplied together. Use the package's Writing and Editing standard for authored instructions and reports. An isolated copy of this entrypoint is not a standalone installer.
